Interfaces

The message contract between items: conventions, transport, and the status of every message

Status snapshot: 26 September 2026. The masters of everything summarised here are in flightTest docs/system/; where a page and a master disagree, the master wins.

Purpose

Bottom line (ELI5): The items talk to each other only through written message contracts. One family of messages, the cue stream, is live and checked. Every other message is still a proposal on paper.

Claim boundary: an interface status is about the message contract: whether a schema exists, whether the producer emits it, whether it was validated live. It says nothing about the quality of what the message carries; for example, a Verified cue still carries modeled, pre-integration SNR predictions.

Follow-up from CR-9 (not yet in the ICD): collection_task and capture_record will need an emitter list and a capture bandwidth, because one capture can cover several emitters (a site may host several, and a capture may be widened to about 12 MHz). detection_list and track_report already carry emitter_id and will need truth_use. Action A-7.

Conventions every message follows

  • Envelope: schema_version, message_type, message_id, source, source_instance_id, sequence_number, generated_utc_ms, flat rather than nested.
  • Encoding: UTF-8 JSON; snake_case names with units in the name; times as integer epoch milliseconds; values rounded to a stated resolution per unit.
  • Fixed shapes for MATLAB: every property present in every message of a run, no field that is sometimes null and sometimes an object, identical keys across array elements, so jsondecode returns the same structs every time (SR-14).
  • Versioning: additionalProperties: false; semantic versions per schema; breaking changes need a major version and a CR.

Cue-stream framing (since 2.0.0): one message per datagram, either plain JSON (first byte {) or compressed (first byte 0xDC, then a dictionary id, then raw deflate with that preset dictionary). The sender chooses once at startup; receivers detect it per datagram. Every datagram fits one Ethernet frame (1472 B). Design, evidence and the decision history are in the CT subsystem record.

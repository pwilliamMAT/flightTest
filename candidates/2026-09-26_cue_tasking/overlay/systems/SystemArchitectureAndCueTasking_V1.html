1. Purpose and current status

Bottom line (ELI5): The testbed now has a written system design with named parts and message contracts. The first part-to-part link is live: a small program on the ADS-B Raspberry Pi watches aircraft and, several times a minute, sends the collection side a message saying which aircraft could be worth collecting on, with which TV tower and when. Those messages were checked on the wire and arrive intact. Nothing in this report says a radar echo has been seen; it says the “ring the bell” message works.

Question this report owns: how is the passive bistatic radar testbed organised as a system, and does the ADS-B Cue Tasker (CT) reliably deliver cues — which aircraft, which DTV illuminator, which time window — to the Resource Manager (RM) side?

On 2026-09-26 the system documents were consolidated in flightTest docs/system/ on main as the master copy: the architecture (ten software items), the interface control document (ICD Draft B, CT messages 2.0.0), the as-built record, change requests CR-1 to CR-8, a verification log, and the raw wire captures. The CT runs as the adsb-cue service on the ADS-B Raspberry Pi and publishes CT 2.0.0 messages to UDP multicast 239.192.10.1:31986, each compressed and fitted into one Ethernet frame. A 15-minute live capture met the ICD acceptance criteria. The first piece of the RM, the MATLAB CueListener, decodes and ranks those cues; it does not yet schedule any collection.

Bottom line (ELI5): The cue stream is small, reliable on this network, and readable from MATLAB, including from a compiled MATLAB app. That makes it safe to build the scheduler on top of. The predicted signal strengths inside each cue are model estimates used to rank aircraft, not detection forecasts.

4. The system as designed, and what exists today

Bottom line (ELI5): The design splits the testbed into ten jobs, each a separate program with a two-letter ID, that talk through defined messages. Today three of them run (the ADS-B receiver, the cue tasker, and the capture scripts), one has its first piece (the resource manager’s listener), and only one message link is live and checked.

The architecture (S02) is written as the source for a MATLAB System Composer model: functional items, hardware, networks, an allocation of items to hosts, and a profile of stereotypes. Every MATLAB item is to become a compiled standalone app on the MATLAB Runtime, Linux first; the CT (Python) and system services are the exceptions. Messages follow one envelope (snake_case, units in field names, epoch-millisecond times, additionalProperties: false, semantic versioning) and carry a development status from the ICD §0 ladder: Proposed → Draft → Implemented → Verified → Frozen (S03).

5. What a cue says, and what it does not

Bottom line (ELI5): A cue is one aircraft’s latest position and predicted path, plus up to eight “opportunities”: for each nearby TV tower, the time windows in which the model expects the aircraft to be worth listening for. It is advice for a scheduler. The resource manager decides priority and antenna pointing.

The SNR in a cue is modeled, pre-integration, and assumed-target SYS-008: it comes from the bistatic radar equation with an assumed 10 dBsm aircraft, the configured receiver (10 dBi, NF 3 dB, 8 MHz), and fixed 1 dB polarization and 2 dB system losses; a window opens where that estimate is at least −10 dB. It contains no coherent-integration gain, no clutter or direct-path residue, and no measured receive-chain behaviour. The CueListener documentation says the same: use it to rank opportunities, not as a detection prediction. Reports 01A and 01B own the program’s illuminator and receive-chain models; this cue model is a separate, simpler ranking model and has not been reconciled with them.

Primary evidence: S03 ICD §2.0–§2.4; S13 bistatic.py and prediction.py; deployed cue configuration.

6. Why the message format changed in one day

Bottom line (ELI5): The first live cues were about 8 kB each, too big for one network packet, so each was chopped into six pieces and lost if any piece was lost; before a temporary cap, the tower list did not fit at all. Measuring where the bytes went showed most were repeated field names. Compressing each message against a shared “dictionary” of those names cut a cue to about 0.7 kB while keeping the readable JSON format and more towers per cue.

CT 1.1.0 (Verified live at 12:34 UTC on 2026-09-26) sent plain JSON. A cue with 11 opportunities was about 25 kB and exceeded the 16,384 B limit, so every opportunity-bearing cue was dropped until a top-3 cap was added (CR-1). Even capped, the median track_cue was 7,962 B: over the 1472 B UDP payload of one Ethernet frame, so it went out as six IP fragments. The byte accounting of that capture found 44.2% field names, 14.0% JSON syntax, and about 17% information; bandwidth was not the constraint (a busy sky of 100 aircraft is estimated at under 0.1% of the 1 GbE data network), datagram size was. SYS-004

Eight encodings were measured on that capture. Only compression or a binary layout fitted one frame. Packed binary was estimated at about the same size as compressed compact JSON while giving up jsondecode, JSON Schema validation, and on-the-wire debugging. The owner decided (CR-5, 2026-09-26): keep JSON, compress each datagram with raw deflate and a fixed, versioned preset dictionary, and clean up the values in a breaking 2.0.0 release (epoch-millisecond times, per-unit rounding, models once per cue, derivable fields removed, fit-to-frame with up to 8 opportunities). Dictionary 1 is a controlled artifact: built reproducibly from 1,707 cues, SHA-256 ca649af0…, immutable once released.

8. The MATLAB consumer and the compiled-app question

Bottom line (ELI5): MATLAB’s own UDP object cannot join a multicast group on Linux, which would have blocked a compiled resource manager. The team used Java classes that ship with MATLAB instead, and proved with a small compiled test app that they work outside a MATLAB session too.

Implemented CueListener SYS-005

Joins the group on the data-network interface through java.net.MulticastSocket, detects plain or compressed framing per datagram, checks the dictionary SHA-256, and applies the ICD receiver rules: highest revision per track, withdrawals, de-duplication, snapshot completeness. It exposes “best opportunities right now” and a window timeline; it does not task anything.

Quantitative anchor: 16 of 16 unit tests pass on a fixture of 20 real compressed datagrams from the Pi (re-run for this report on the branch head, R2026a).

Demonstrated Compiled-app probe SYS-006

A MATLAB Compiler standalone app, run on the MATLAB Runtime on the collection desktop, joined the live group, decoded heartbeats, a snapshot and a track_cue, and inflated a dictionary-compressed cue byte-exact. It needed only the base, standard and graphics runtime add-ons, not the Instrument Control Toolbox.

Quantitative anchor: 1,005 B compressed → 7,958 B JSON, byte-exact; decode 0.1–0.4 ms per cue plus about 0.3 ms jsondecode.

Investigated Why not udpport SYS-006

configureMulticast raises PlatformNotSupported on Linux and cannot choose the joining interface. The desktop’s default route is Wi-Fi, so an unspecified join would listen on the wrong network. CR-2 proposes stating the Java method in the ICD and adding it to the compiler deployability checks.

Status: CR-2 open; deployability verified.

9. As-built deployment and the time-source finding

Bottom line (ELI5): The cue tasker restarts itself if the ADS-B feed is not up yet, and survived a Pi reboot. While setting it up, the team found the Pi’s clock had been running about 15 seconds slow, because its GPS time reference was not locked and it had no internet time. That is now fixed through the desktop, but it matters for any earlier data timed by the Pi.

Installed and checked SYS-002
  • adsb-cue runs adsb-console --headless against the local dump1090, with an observer file holding only the real receive site (the built-in defaults had produced opportunities for a receiver that does not exist).
  • It exits 1 if the SBS source is unreachable; systemd restarts it after 10 s. After a Pi reboot on 2026-09-25 it connected on the second try and cues resumed.
  • SIGTERM sends a final stopping heartbeat.
  • One prediction costs about 407 ms of Pi CPU (2 observers × 16 emitters, before the observer list was reduced to one site).
Time source: not as designed SYS-007
  • Design: a GPS + 1-PPS stratum-0 source on the Pi disciplines every host.
  • As built: chrony syncs from internet NTP through a NAT on the collection desktop; GPS/PPS reference clocks are configured but not locked.
  • Before that, on 2026-09-25, the Pi was measured 14.9 s slow. Every cue timestamp and every ADS-B truth record written by the Pi shifts by that offset.
  • How long the offset existed, and its size at the time of earlier collections, is unknown (one reading, raw data not kept).
Consequence for earlier evidence: ADS-B truth timestamps written on the Pi before 2026-09-25 21:07 UTC cannot be assumed accurate to better than the unknown clock offset of the time. This includes the ADS-B context packaged with collections described in Report 02 and the aircraft-overlap analysis of the 2026-09-25 tracking-scan diagnostic. This report does not claim the offset explains any earlier result; it has not been assessed. SYS-007

Primary evidence: S04 As-Built, S05 CR-8, S06 Pi clock entries, S13 service unit.

12. Claim boundary and non-claims

Bottom line (ELI5): This report proves that a message gets from one computer to another intact and can be read where it is needed. It proves nothing about aircraft echoes.

This report establishes
  • a controlled system architecture and ICD, with as-built, change-request, and verification records;
  • an installed CT service on the Pi publishing CT 2.0.0 cues;
  • on one named 15-minute live capture, a cue interface that met every ICD acceptance criterion, with every datagram in one frame;
  • a MATLAB receiver and a compiled-app route that can consume the stream;
  • that the Pi’s time source is not operating as designed and was 14.9 s slow before 2026-09-25 21:07 UTC.
This report does not establish
  • any passive-radar detection, track, or localization, or any operational Pd or Pfa;
  • that a predicted SNR or window will yield a detection; predicted SNR is a modeled, pre-integration estimate for an assumed 10 dBsm target;
  • that the Resource Manager schedules anything; it does not yet;
  • timing accuracy of cues or ADS-B truth beyond the NTP state reported;
  • collection suitability, reference-path adequacy, or any closure of the blockers in Report 06;
  • loss-free delivery beyond the capture analysed.
Vocabulary: “Verified” in this report always means the ICD §0 level: validated live on the wire with zero errors by a capture tool. It is shown as Demonstrated in the family status vocabulary. It never means a verified radar measurement.

13. Method

Capture. adsb-cue on the Pi (CT 2.0.0, deflate_dictionary, dictionary 1) published to the multicast group; on the collection desktop, ADSB-remoter tools/cue_capture.py joined the group on the data-network interface with an 8 MiB receive buffer, decoded each datagram, validated it against schemas/*-2.0.0.json, and summarised gaps, duplicates, ordering, snapshot consistency, sizes, and one-frame fit. Raw wire bytes were kept (base64 per datagram), so the decoded form can be rebuilt.

Reproduction for this report. The figure script decodes the committed wire capture with dictionary 1 (SHA-256 checked), validates every message with jsonschema against the 2.0.0 schemas, recomputes the counts, and cross-checks them against the committed capture summary: datagrams, schema failures, gaps, one-frame fit, largest datagram, aircraft, median cue sizes, message counts, and revision reasons all reproduced exactly. The same script measures the 1.1.0 plain-JSON capture line by line (median track_cue 7,962 B, 14 of 46 over one frame, matching S08) and draws Figures 2–4.

Re-runs at report time. CT test suite at 55062fc: 81 passed. CueListener tests at 94bf924 (R2026a): 16 of 16 passed. Both are diagnostic checks of the code at those commits, not new field evidence.

Not re-derived here. The Pi clock readings, compiled-app probe, 1.1.0 byte accounting, and replay run are taken from S06, S08 and S10 as recorded.

15. Glossary

ADS-B
Aircraft broadcasts of identity, position and velocity. Here it drives the cue tasker and is also the truth source for scoring; the two uses must be kept apart in any truth-blind evaluation.
Cue / track_cue
A CT message for one aircraft: its state, predicted path, and up to 8 ranked opportunities.
Opportunity
One (observer, DTV emitter) pair for an aircraft, with current predicted geometry and SNR and the time windows in which the modeled SNR clears the threshold.
Snapshot
A full resend of every cue-eligible track every 60 s, bracketed by begin and end messages, so a receiver that lost a datagram recovers within a minute.
Preset dictionary
A fixed block of typical message text that sender and receivers share, so the compressor can refer to it instead of repeating field names. Dictionary 1 is identified by id and SHA-256 and never changes.
One frame
1472 B of UDP payload, the most that fits one 1500-byte Ethernet frame without IP fragmentation.
ICD status ladder
Proposed → Draft → Implemented → Verified → Frozen (ICD §0). Verified means validated live on the wire with zero errors.
WI-7 criteria
